## 一、一句话结论

固件**可以编译、可以烧录、可以通过串口回应 `help`**，但**电机不会动、编码器不会计数、
LED / 按键 / 拨码开关全部无效、电流读数无意义**。当前状态是"串口控制台可用的骨架"，
**不是**可上机的电机控制器。

设计文档（`../RST夹取端控制设计方案.txt`）承诺的三级串级控制（位置环 1kHz /
速度环 5kHz / 电流限幅 20kHz）、上电自动标定、`P<>U<>L<>` 流式协议，
**在代码中均不存在**。

**完成度：约 30%**（BSP/外设初始化 ~75%，应用与控制层 ~5%）

## 三、致命问题：控制循环一次都不会执行

这是当前最重要的单点问题，其余控制相关的功能缺失都被它掩盖。

### 3.1 `MX_TIM6_Init()` 从未被调用

全工程对 `MX_TIM6_Init` 的引用只有两处：

| 位置 | 内容 |
|---|---|
| `control/Core/Src/tim6.c:22` | 函数**定义** |
| `control/control.ioc:179` | CubeMX 的 functionlistsort 配置项（非代码） |

`control/Core/Src/main.c:95-104` 的外设初始化列表中**没有** `MX_TIM6_Init();`：

```c
  MX_GPIO_Init();
  MX_DMA_Init();
  MX_ADC1_Init();
  MX_CAN_Init();
  MX_TIM1_Init();
  MX_TIM2_Init();
  MX_TIM3_Init();
  MX_TIM4_Init();
  MX_TIM8_Init();
  MX_USART1_UART_Init();
  /* ← 缺 MX_TIM6_Init(); */
```

### 3.2 后果：静默失败

`htim6.State` 因此停留在 `HAL_TIM_STATE_RESET`。而
`control/Core/Src/control_loop.c:79` 调用的 `HAL_TIM_Base_Start_IT()`
第一件事就是检查状态（见 HAL 库源码）：

```c
if (htim->State != HAL_TIM_STATE_READY) { return HAL_ERROR; }
```

即**直接返回错误，定时器从未使能，中断永不产生，`RST_ControlLoop20kHz()`
永不执行**。返回值没有被检查，所以串口仍会照常打印
`Control loop started at 20kHz`（`main.c:117`）—— 这是一条假消息。

### 3.3 自检方法

`info` 命令的 `Loop Cnt` 字段（`debug_console.c:239`）读取 `g_rst.loop_count`。
该变量在 `control_loop.c:41` 被置 0 后，**全工程再无任何自增语句**。
因此 `Loop Cnt` 恒为 0。

> 各操作手册中"`Loop Cnt` 在增加 → 20kHz 控制循环正常"的判据本身是对的，
> 但当前代码下它**必然不会增加**，且即使补上 TIM6 初始化也不会增加
> （因为没有人写 `loop_count++`）。

### 3.4 修复

`main.c:104` 之后加一行 `MX_TIM6_Init();`，并在 `tim.h` 中补声明。
同时应检查 `HAL_TIM_Base_Start_IT()` 的返回值而非忽略。
若要让 `Loop Cnt` 可用，需在 `RST_ControlLoop20kHz()` 内加 `g_rst.loop_count++;`。

## 四、致命问题：GPIO 配置已被 CubeMX 重新生成时清除

`control/Core/Src/gpio.c` 的 `MX_GPIO_Init()` 当前**只有三行时钟使能**
（`gpio.c:42-50`）：

```c
void MX_GPIO_Init(void)
{
  __HAL_RCC_GPIOC_CLK_ENABLE();
  __HAL_RCC_GPIOA_CLK_ENABLE();
  __HAL_RCC_GPIOD_CLK_ENABLE();
}
```

**没有 `__HAL_RCC_GPIOB_CLK_ENABLE()`，没有 `__HAL_RCC_GPIOE_CLK_ENABLE()`，
没有任何引脚的 `HAL_GPIO_Init()` 调用。**

历史版本曾在此函数内手写过 LED / 按键 / 拨码 / 电机方向脚的配置，
但因为那段代码位于 CubeMX 生成区（`USER CODE BEGIN 2` 标记在函数**之外**，
`gpio.c:52`），且 `.ioc` 设了 `DeletePrevious=true`，重新生成时被整段删除。

### 直接后果（全部为运行期静默失效）

| 功能 | 涉及引脚 | 当前状态 |
|---|---|---|
| 电机方向控制 | PB0/PB1/PB5/PB12/PB13/PB14 | **完全无效** — GPIOB 时钟未开，引脚未配置为输出 |
| LED × 4 | PE2–PE5 | **完全无效** — GPIOE 时钟未开 |
| 按键 × 2 | PE0/PE1 | **完全无效**，`btn` 命令返回无意义值 |
| 拨码开关 | PC0–PC3 | GPIOC 时钟已开，但引脚未配为上拉输入，`dip` 读数不可信 |

因此 `motor_driver.c` 的 `Motor_SetDirection()` / `Motor_Sleep()` /
`Motor_Brake()` 虽然代码本身写得是对的（TB6612 真值表正确），
**但对未使能时钟的 GPIOB 写寄存器不产生任何电平变化**。

### 修复

把这些引脚配置移到 `USER CODE BEGIN 2` 之后的独立函数（例如 `RST_GPIO_Init()`），
由 `main.c` 显式调用；或在 CubeMX 的 `.ioc` 里正式登记这些引脚。
**前者更安全** —— 只要配置留在生成区，下一次 Generate Code 就会再丢一次。

## six、控制算法：完全未实现

`control/Core/Src/control_loop.c` 实际共 **141 行**（多份文档声称"241 行完整实现"）。
`RST_ControlLoop20kHz()` 的真实函数体（`control_loop.c:123-141`）：

```c
void RST_ControlLoop20kHz(void)
{
    ReadEncoders();
    ReadCurrents();

    /* 3. 简单的位置控制 (TODO: 实现完整的 PID) */
    for (int i = 0; i < MOTOR_COUNT; i++) {
        if (!g_rst.motor[i].enabled) {
            g_rst.motor[i].pwm_output = 0;
        } else {
            // 完整实现需要 PID 控制器
            g_rst.motor[i].pwm_output = 0;
        }
    }
}
```

对照文档承诺，逐项核实结果：

| 文档声称已实现 | 代码实际情况 |
|---|---|
| PID 控制器（含积分限幅、微分滤波） | **不存在**。`pid.kp/ki/kd`、`pid_integral`、`pid_last_error` 只被清零和由 `pid` 命令赋值，**没有任何一行运算读取它们**。 |
| 归零状态机（堵转找零） | **不存在**。`homing` / `homing_step` / `homing_stall_cnt` 只在 `RST_SafeStartup()` 里被清零，此后无任何读写。`calibrated` 永远为 `false`。 |
| 位置模式 `MODE_POSITION` | **不存在**分支实现 |
| 速度模式 `MODE_VELOCITY` | **不存在**分支实现 |
| 力矩模式 `MODE_CURRENT` | **不存在**分支实现 |
| 堵转检测（电流 + 速度双重判断） | **不存在**。`stalled` 与 `STATE_STALL` 从未被置位。 |
| 电流限幅 / 过流保护 | **不存在**。代码中**没有任何电流上限常量**；文档反复提到的 `STALL_CURRENT_MA` 和 `STALL_VELOCITY_LIMIT` 在整个工程里**未定义**。 |

此外还有一个结构性缺陷：即使补上 PID，`pwm_output` 算完后**从未调用
`Motor_SetPWM()`**，数值只写进结构体，永不下发到硬件。

`rst_config.h:265,267` 声明的 `RST_Loop1kHz()` 与 `RST_ControlInit()`
**没有任何定义**，属残留声明（因无人调用，链接期不报错）。

## 七、传感器读取的具体缺陷

### 7.1 编码器角度有 +4915° 固定偏置

`RST_SafeStartup()`（`control_loop.c:64-70`）把三个计数器预置为 32768
以避开 16 位回卷。但 `ReadEncoders()`（`control_loop.c:101`）用**绝对计数**算角度：

```c
g_rst.motor[i].current_angle = (float)cnt_now * 360.0f / ENC_COUNTS_PER_REV;
```

32768 × 360 / 2400 = **4915.2°**。即上电后 `current_angle` 不是 0 而是 4915.2°，
且这个零点偏置从未被减掉。速度计算（`control_loop.c:104`）的 delta 回卷处理
（`±32768` 判断）是**正确**的，只有角度是错的。

修复：记录 `zero_offset_cnt`，角度用 `(cnt_now - zero_offset_cnt)` 计算；
或引入圈数累加以支持多圈位置。

### 7.2 ADC 只会转换一轮

`HAL_ADC_Start_DMA()` 终于被调用了（`control_loop.c:73`，相对旧版是真实修复），
但 `control/Core/Src/adc.c:48,50` 仍是：

```c
hadc1.Init.ContinuousConvMode = DISABLE;
hadc1.Init.ExternalTrigConv = ADC_SOFTWARE_START;
```

非连续 + 软件触发 + 无人重复触发 = 完成一轮 3 次转换后停住。
`current_ma` 之后永远是同一组陈旧值。DMA 虽是 Circular，也不会再被喂数据。

修复：`ContinuousConvMode = ENABLE`（或由 TIM 触发）。

### 7.3 上夹电流通道采不到（旧问题，未修）

`control/Core/Src/adc.c:79` 只改了 Rank 没改 Channel：

```c
sConfig.Channel = ADC_CHANNEL_4;  /* adc.c:60  Rank1 = PA4  Pitch  */
sConfig.Rank = ADC_REGULAR_RANK_1;
...
sConfig.Channel = ADC_CHANNEL_3;  /* adc.c:70  Rank2 = PA3  下夹   */
sConfig.Rank = ADC_REGULAR_RANK_2;
...
sConfig.Rank = ADC_REGULAR_RANK_3;  /* adc.c:79  ← Channel 仍是 3！ */
```

`.ioc` 中同样错误（`ADC1.Channel-2#... = ADC_CHANNEL_3` 与
`ADC1.Channel-3#... = ADC_CHANNEL_3`），说明是 CubeMX 里就配错了。

后果：**PA5（上夹电流）永远不被采样，PA3 被采两次。**
且 `rst_config.h:123-125` 声称的 rank↔电机对应关系与 `adc.c` 不符。
正确应为 Rank1=CH4、Rank2=CH5、Rank3=CH3。

### 7.4 ADC 采样时间过短

三个 rank 均为 `ADC_SAMPLETIME_1CYCLE_5`（`adc.c:62`）。ADC 时钟 = 72MHz/6 = 12MHz，
采样窗仅 0.125 µs。设计文档要求 239.5 cycles。
对 INA180 输出接 RC 滤波的场合大概率不足，读数会偏低并串扰。
**（此项未经实测，因缺原理图无法判定 INA180 输出阻抗，标记为高风险而非确定缺陷。）**

## 八、CAN：波特率与文档不符 1.8 倍

`control/Core/Src/can.c:41,44,45`：`Prescaler=4, BS1=13TQ, BS2=2TQ`。
CAN1 挂在 **APB1 = 36MHz**（不是 APB2 的 72MHz）：

```
36 MHz / (4 × (1 + 13 + 2)) = 562 500 bps
```

`.ioc` 自己也算出 `CAN.CalculateBaudRate=562500`。

而 `rst_config.h:48` 写 `CAN_BAUD_RATE 1000000U`，
`debug_console.c:238` 还会向用户打印 `CAN ID: %d (1Mbps)`，
多份文档也写 1Mbps。**上位机按 1Mbps 配置将完全无法通信。**

另：`can.c:47` `AutoBusOff = DISABLE`，总线关闭后不自动恢复，
而软件中没有任何 CAN 错误处理。

## 十、PWM 频率与控制频率的量级冲突（设计层问题）

`tim.c:50,52`（TIM1）与 `tim.c:253,255`（TIM8）：`PSC=71, ARR=999`，挂 APB2 72MHz：

```
72 MHz / 72 / 1000 = 1 000 Hz
```

即 **PWM = 1kHz**，而计划的控制环是 20kHz —— 控制频率是 PWM 频率的 20 倍，
每个 PWM 周期内更新 20 次占空比在物理上无意义。且 1kHz 处于可听频段，
直驱有刷电机会明显啸叫。

这不是填空 `RST_ControlLoop20kHz()` 能解决的，**定时器方案本身需要重新设计**。
建议：PWM ≥ 16kHz（超出可听范围），控制环 ≤ PWM/8。

另有标度不自洽：`rst_config.h:63,64` 定义 `PWM_ARR=999` 但 `PWM_MAX_DUTY=1000`，
`Motor_SetPWM` 允许 duty 取到 1000 → 写入 CCR=1000 > ARR=999。
硬件表现为恒 100% 输出，可接受但不严谨。而 `PWM_ARR` 宏从未被 `tim.c` 使用
（`tim.c:52` 是硬编码 999），两者失步不会有任何报错。

## 十一、安全机制：基本为空

| 保护项 | 设计要求 | 当前状态 |
|---|---|---|
| 电流限幅 | 正常 1.0A / 标定 0.3A / 最大 2.0A，20kHz 检查，不可绕过 | **无**。无上限常量，无比较逻辑。 |
| 堵转检测 | 超限 500ms → 降为维持电流 | **无** |
| 通信超时 | 500ms 保持 / 2s 停止 | **无**。`Motor_SetPWM` 设定值无限期保持，上位机断线或程序跑飞后电机继续转。 |
| 急停 | `STOP` 命令 / 按键 | **无**。按键 GPIO 未配置（见第四节），无 `STOP` 命令。 |
| 看门狗 | — | **无 IWDG / WWDG**（`.ioc` 外设列表中不存在） |
| 机械限位软保护 | — | **无** |

`Error_Handler()`（`main.c:192-201`）是 `__disable_irq()` + 空死循环：
不指示、不输出、**不关闭 PWM**、不置方向脚为惰行。
`tim.c` / `adc.c` / `can.c` / `usart.c` 中有 20+ 处失败会跳到这里。
若在 PWM 已启动后触发，电机可能保持通电而 MCU 已停止响应。
**至少应先对三路调用 `Motor_Sleep()` 再挂起。**

> 当前"电机不会动"这一事实反而掩盖了安全机制的缺失。
> **在补齐 PWM/GPIO 启动之前，必须先把电流限幅和指令超时写进控制环**，
> 否则第一次电机真正转起来时没有任何软件保护。

## 十二、串口协议：仍未实现

设计文档（`../RST夹取端控制设计方案.txt` 第七节）规定的协议：

```
指令帧   P<0-255>U<0-255>L<0-255>\n      50~100Hz
状态帧   A<p> A<u> A<l> S<status>\n
控制命令 CALIB / STOP / ENABLE / DISABLE / PING
```

对 `CALIB`、`STOP`、`ENABLE`、`DISABLE`、`PING` 的全工程检索**零命中**
（仅有的 `NO_CALIB` 是枚举名 `rst_config.h:189`）。

实际实现的是一套面向人工调试的交互式 shell（`debug_console.c:58-71`），
11 条命令：`help / info / led / btn / dip / pwm / enc / adc / can / pid / reboot`。
这是空格分词 + 大小写不敏感查表，与紧凑字符流协议 `P123U45L67`
在解析架构上不兼容，**需另写解析器**，不是改几行的事。

**没有目标角度下发通道**：`goal_angle` 除了在 `control_loop.c:50` 被清零外，
全工程无写入点。也没有 `enable` 命令 —— `Motor_t::enabled` 恒为 `false`
（`control_loop.c:47`），意味着即使控制环跑起来也会走"禁用→刹车"分支。

## 十三、已确认修好的问题（相对上一版本的真实进展）

这些是本次重构的实质成果，值得记录：

1. **ISR 死锁已消除。** 旧版在 USART1 中断里直接解析命令并调用 `HAL_Delay()`，
   而 SysTick 优先级(15) 低于 USART1(0)，`HAL_GetTick()` 冻结 → `led N blink`
   和 `reboot` 会 100% 挂死。现在 `Console_RxCallback()`（`debug_console.c:136`）
   只做回显和入队，解析移到主循环的 `Console_Process()`（`main.c:130`），
   `HAL_Delay` 因此运行在线程上下文，**不再死锁**。
2. **命令重放已消除。** `Console_Process()` 在每条路径末尾都清了
   `cmd_line[0] = '\0'`（`debug_console.c:191,210,216`），
   裸回车不会再重复执行上一条命令。旧版会，且对 `pwm 0 1000` 是安全隐患。
3. **`app_main.c` 已删除。** 旧版那个引用了不存在的 `hcan1` 句柄、
   不在构建清单里的孤儿文件已消失。
4. **`HAL_ADC_Start_DMA()` 已被调用**（`control_loop.c:73`），
   旧版完全没有启动 ADC。（虽然还有 7.2 / 7.3 的问题。）
5. **TIM6 的 ISR 侧接线是完整正确的**：`stm32f1xx_it.c:247` 有 `TIM6_IRQHandler`、
   `:265-269` 有 `HAL_TIM_PeriodElapsedCallback` 分发，

## 十四、遗留的次要缺陷

- `Console_Println()`（`debug_console.c:99-103`）：C99 `vsnprintf` 返回的是
  "未截断时的应有长度"。若格式化结果超过 254 字符，`len > 254`，
  `buf[len++]` 越界写栈。MDK 工程 `useUlib=0`（未启用 MicroLIB），
  用的是符合 C99 的完整库，所以该语义成立。当前调用点输出都短，属**潜伏缺陷**；
  `%s` 接到长字符串即触发。`vsnprintf` 返回负值时 `buf[-1]` 同样越界。
- `debug_console.c:197` 的注释称"避免 strcasecmp 在 MicroLIB 中不存在"，
  但工程实际**未启用** MicroLIB，与多份文档"勾选 Use MicroLIB"的说法矛盾。
- 退格处理（`debug_console.c:156-159`）只回退索引，不发送擦除序列 `\b \b`，
  终端显示与缓冲内容不一致。
- `g_rst` 未加 `volatile`，而优化等级为 `-O3`。目前主循环不读控制相关字段，
  尚未暴露；补上控制环后（在 ISR 里读 `goal_angle` / `pid.kp`），
  编译器可能把读取提到循环外，导致上位机改参数不生效。
- `can_node_id` 恒为 0（`control_loop.c:39`）—— 拨码开关从未被读取，
  而多份文档的示例输出写的是 `CAN ID: 8`。
- `.ioc` 中 `CompilerLinker=GCC` 与实际 `MDK-ARM` 工具链冲突；
  `UnderRoot=false` 与文档要求的 "Generate Under Root" 不符。
